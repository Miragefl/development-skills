# Java 编码规范（可维护性 + 设计模式）

供 flow 在「实现」步骤遵循。目标：写出别人（和三个月后的自己）看得懂、改得动的代码。每条一句话原则 + 何时用。

## 1. 总则（可维护性基础）

- **KISS**：能用简单方案别炫技。复杂度要为真实需求买单。
- **YAGNI**：别为"以后可能用得上"预留抽象。用到了再抽。
- **DRY**：重复三次就抽。但别为 DRY 把不相关的东西硬塞一起。
- **小函数**：一个方法 ≤30 行，只干一件事。超过就拆。
- **见名知意**：`processOrder()` 好，`doStuff()` 坏。别省字母到看不懂。
- **无魔法值**：`if (status == 3)` 坏，`if (status == OrderStatus.PAID)` 好。常量/枚举。
- **低耦合高内聚**：改一个功能只动一个地方；一个类里的东西都相关。

## 2. SOLID（Java 视角）

- **S 单一职责**：一个类/方法只有一个变更理由。Controller 不写业务，Service 不碰 SQL 细节。
- **O 开闭原则**：加功能靠新类/新分支实现，不改老代码。策略模式是常用手段。
- **L 里氏替换**：子类能完整替代父类，别在用父类的地方偷偷 instanceof。
- **I 接口隔离**：接口按消费方裁剪，别造"全能大接口"。多个窄接口好过一个胖接口。
- **D 依赖倒置**：依赖接口/抽象，不依赖具体类。Spring 里 `@Autowired` 注入接口实现就是 DIP。

## 3. 后端分层实战

- **三层职责**：
  - `Controller`：接收参数、校验、编排调用、返回 VO。**不写业务逻辑**。
  - `Service`：业务逻辑、事务边界。**不直接拼 SQL 细节**（用 Repository/Mapper）。
  - `Repository/Mapper`：数据访问。**不掺业务判断**。
- **对象分层**：`DTO`(入参) · `VO`(出参) · `Entity`(表映射) · `Param`(内部传递)。**别拿 Entity 直接返给前端**。
- **构造器注入**：用 `@RequiredArgsConstructor` + `final` 字段，别用字段注入（`@Autowired` 写在字段上）。
- **统一异常**：`@RestControllerAdvice` + 自定义业务异常，Controller 不写 try-catch 堆。
- **事务边界**：`@Transactional` 标在 Service 方法，别标 Controller；只读查询用 `@Transactional(readOnly=true)`。

## 4. GoF 设计模式（按场景用，别为用而用）

- **策略模式**：替换一坨 `if-else`/`switch`（不同支付方式、折扣算法）。何时用：分支会持续增加。何时别用：就两三个固定分支。
- **工厂方法**：对象创建逻辑复杂或需按类型造。何时用：`new` 时要一堆判断。何时别用：直接 `new` 就够。
- **建造者**：构造参数多（≥4）或有可选参数。Lombok `@Builder`。何时用：构造函数参数爆炸。
- **模板方法**：流程固定、各步可变。何时用：多个类有相同骨架不同细节。何时别用：流程就一处。
- **观察者/事件**：解耦"做完 X 后要做 Y"。Spring `ApplicationEvent`。何时用：Y 不该阻塞 X、或有多个 Y。何时别用：就是顺序调用。

## 5. 测试友好

- **依赖注入便于 mock**：依赖走构造器注入，单测能传 mock。别在方法里 `new` 依赖。
- **单一职责好测**：一个方法只干一件事，测试用例才清晰。
- **纯函数优先**：无副作用的方法（输入→输出）最好测。把 IO/时间/随机隔离到边界。
- **接口先行**：依赖接口，mock 时只 mock 接口不碰实现。
- **别滥用静态方法**：静态方法难 mock、难扩展。工具方法才用 `static`，业务逻辑别用。

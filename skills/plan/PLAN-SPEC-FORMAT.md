# 精简版 Spec 与 Plan 格式

供 plan（大需求规划）使用。原则：**够用就行，不写长文**。区别于 superpowers 的几十页文档——这里一页 spec + 一个 task 清单。

## 何时走 plan/spec flow（使用者自决）

- **大需求**（走 plan/spec）：跨模块、架构级、跨会话才能干完、多人协作、复杂业务规则。
- **小/中需求**（直接 flow）：一处改动、一个 bug、单个功能模块、单会话能完。

使用者判断，AI 可建议但最终使用者定。拿不准就选直接 flow——文档随时能补，别为小活儿套重壳。

## Spec 格式（落 `docs/specs/<需求名>.md`，一页纸）

```md
# <需求名>

## 目标
<一句话：要解决什么问题>

## 约束
- 技术栈/版本（读 PROJECT-CONTEXT.md）
- 边界（做什么、不做什么）

## 模块拆解
- <子模块A>：<职责>
- <子模块B>：<职责>

## 数据模型（涉及建表时）
- 新增/改动的表：<表名、核心字段、关系>
- 设计遵循：../doc/DB-DESIGN.md（主键 / 索引 / 命名 / 范式）

## 关键决策
- <决策点>：选 X 不选 Y，因为...

## 风险
- <风险>：<对策>
```

## Plan 格式（落 `docs/plans/<需求名>.md`，task 清单）

```md
# <需求名> 实现计划

> 关联 spec: ../specs/<需求名>.md

### Task 1: <子模块/步骤>
- 改：`<文件路径>`
- 验证：`<命令或检查>`
- [ ] 完成

### Task 2: ...
```

## 原则

- **spec 一页**：超过一页说明想得还不够清楚，或需求该再拆。
- **plan 是清单**：每个 Task 能独立验证、改明确的文件。
- **不强制顺序**：plan 写完可调整，不是签了字的合同。
- **小需求别用**：别为小改动套这层，浪费。
